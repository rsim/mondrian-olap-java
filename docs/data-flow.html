The life of an MDX query

One MDX statement, traced end to end through the engine — from the mondrian-olap JRuby gem down to SQL and back. Stages 1–4 run once, while the statement is prepared; stages 5–6 run on every execute. A prepared Query is fully resolved and compiled, and can be executed repeatedly.

Prepare-time — parse, bind, compile (static) Execute-time — evaluate cells (runtime) SQL / phase-loop hot path
Prepare time runs once — in the prepared-statement constructor
1

Entry

MDX string → olap4j prepared statement

The gem drives Mondrian purely through the olap4j API. Connection#connect loads MondrianOlap4jDriver by reflection and unwraps a native RolapConnection; prepareOlapStatement(mdx) registers the statement with the engine's MondrianServer.

MondrianOlap4jDriver MondrianOlap4jConnection MondrianOlap4jPreparedStatement MondrianServer
2

Parsing

MDX text → Query AST

Wrapped in a Locus execution context, the JavaCC-generated MdxParserImpl runs its statementEof() production; grammar actions call Parser.FactoryImpl#makeQuery. Product: a mondrian.olap.Query of mondrian.mdx nodes — Id (unbound names), UnresolvedFunCall (operators/functions), literals.

JavaccParserValidatorImpl MdxParserImpl Parser.FactoryImpl mondrian.olap.Query
3

Resolution & validation

names → schema objects, calls → ResolvedFunCall

Query#resolve registers WITH members/sets, then IdBatchResolver batch-binds every Id against the SchemaReader (batched because member lookup can hit SQL). The QueryValidator walks the tree; FunTable lookup arbitrates candidate resolvers, turning each call into a typed ResolvedFunCall.

IdBatchResolver QueryValidator FunTable BuiltinFunTable ResolvedFunCall
4

Compilation

Exp trees → Calc trees

The final step of Query#resolve: BetterExpCompiler compiles each formula, axis (Query.axisCalcs) and slicer (Query.slicerCalc) into executable Calc objects. MDX is never interpreted from the AST — each FunDef#compileCall emits a typed calc subtree (MemberCalc, TupleCalc, list/iterable calcs, …).

BetterExpCompiler AbstractExpCompiler Calc MemberCalc · TupleCalc
Execute time runs on every executeQuery()
5

Execution — the phased cell-loading loop

Query → RolapResult (evaluated cells)

executeQuery() creates a MondrianOlap4jCellSet — which is the Execution (cancellation/timeout state). It routes through the RolapResultShepherd watchdog into RolapConnection#executeInternal, whose RolapResult constructor is the entire evaluation algorithm: it builds a RolapEvaluator (current member of every hierarchy) and a FastBatchingCellReader, evaluates the slicer, then each axis.

RolapResult RolapResultShepherd RolapEvaluator FastBatchingCellReader
Stage 5.3 — the phase loop

evaluate → batch → SQL → re-evaluate

Mondrian never fetches one cell with one query. It runs speculative passes.
01
Evaluate a pass

executeStripe recurses over axes, positioning the shared CellKey, calling evaluateCurrent at each coordinate.

02
Record, don't fetch

On a cache miss FastBatchingCellReader#get records a CellRequest and returns valueNotReadyException. The cell stays unset.

03
Batch → SQL

loadAggregations groups requests by AggregationKey, serves from segment caches / rollup, else emits SqlQuery. Results become Segments.

04
Re-evaluate

Run again against warm caches. Calculated members can cascade new base-cell requests — loop until a pass has zero misses.

Control flow, not errors: valueNotReadyException and CellRequestQuantumExceededException must propagate to the loop — evaluation-path code must never swallow them. Runaway queries stop at MaxEvalDepth; request floods chunk at CellBatchSize. Segments are cached schema-wide, beyond the query.
6

Result consumption

RolapCell → olap4j → Mondrian::OLAP::Result

RolapResult#getCell returns a RolapCell; getFormattedValue applies the stored ValueFormatter via mondrian.util.Format. olap4j wraps it as MondrianOlap4jCell, and the gem's Result walks axes and values lazily, converting Java to Ruby (BigDecimal, CLOB → String). NON EMPTY axes are filtered here where not already pushed into SQL.
